# Standaardinrichting van een repo

De workflows zijn maar de helft. De andere helft is de inrichting van elke repo, die in geen enkele PR langskomt: branchprotectie, verplichte checks, environments, variabelen en secrets. Een steekproef van zes repo's laat zien dat die uiteenloopt ([audit](auditbevindingen.md#audit-config)). v2 legt de standaard vast en levert een script dat elke repo daaraan toetst.

## De standaard

| Onderdeel | Elke repo | Wanneer |
| --- | --- | --- |
| Aanroepende workflows | `check-pr.yml` met job-id `run-check-pr`, op `pull_request` met `types: [opened, synchronize, reopened, edited]` en zonder `branches:`-filter, zodat een andere base de check opnieuw laat draaien. Eén CI-bestand, `name: Continuous Integration`, met de job `run-ci`; frontend en backend draaien via turbo in diezelfde job. Een Swarm-project zet de ci-images-aanroeper als tweede job `run-ci-images` in datzelfde bestand, niet in een eigen bestand: één bestand geeft één `workflow_run`-event en dus één gate-run ([besloten](../beslissingen.md#decided)). Een CD-aanroeper met de jobs `gate` en `deploy`. Job-id's horen bij de afspraak: de naam van de verplichte check is `<job van de aanroeper> / <aangeroepen job>`. | altijd |
| Branchprotectie, `main` en `develop` | Verplichte checks `run-check-pr / pipeline` en één `<job> / pipeline` per CI-job: `run-ci / pipeline`, en `run-ci-images / pipeline` in een Swarm-project. De bron van elke verplichte check staat op GitHub Actions, zodat geen ander token een status met die naam kan zetten. Branches moeten up-to-date zijn. Eén goedkeurende review, en review van de code owners verplicht, met één uitzondering: **senior developers mogen hun eigen PR mergen** ([besloten](../beslissingen.md#decided)). Dat werkt via de rol: het team `senior-developers` is admin op de repo, `developers` heeft push. **Twee rulesets per branch**, omdat een bypass in een ruleset álle regels van die ruleset overslaat: één met de review, force-push- en verwijderregels, waarin admins (bypass `RepositoryRole: admin`, alleen voor PR's) de review mogen overslaan; en één met alleen de verplichte checks, **zonder bypass**, zodat ook een senior nooit langs een rode check merget. De klassieke protectie van nu (`enforce_admins: false`) kan dat niet scheiden: daar slaat een admin review én checks over. `setup-consumer.sh` zet de twee rulesets en haalt de klassieke protectie weg. Geen force push. Dezelfde regels op beide branches, per repo ingesteld ([besloten](../beslissingen.md#decided)): afwijken kan, en de audit maakt het zichtbaar. | altijd; `acceptance` wanneer die er is |
| Environments | `integration` (CI draait daarin), `staging`, `production`, en `acceptance` zodra die branch bestaat; `github-pages` maakt GitHub zelf aan voor cd-pages. Alle deploy-credentials staan als secret op deze environments, nergens anders ([besloten](../beslissingen.md#decided)). In kleine letters. GitHub negeert hoofdletters in environmentnamen, maar de YAML, de branchmapping van de gate en de namen van de 1Password-vaults gebruiken overal kleine letters. | altijd |
| Branchregels per environment | Dit is wat principe 4 afdwingt; de gate in de YAML kan een branch zelf wegschrijven. `staging`: alleen `develop`. `acceptance`: alleen `acceptance`. `production`: alleen beschermde tags (`v*`), plus `main` als de repo `main=production` in `branch-targets` zet; verplichte reviewers. Een run op elke andere branch, ook een handmatige, weigert GitHub vóór de job start, en de environment-secrets blijven dicht. Een handmatige productiedeploy start je daarom vanaf de tag van de nieuwste release, niet vanaf `main`. `integration`: geen regels, want CI draait op elke branch; daarom staat er niets in dat een PR niet mag zien. | altijd |
| Environmentvariabelen | `OP_VAULT` en `OP_ITEM` op `staging` en `production`. Op de environment, niet op de repo: waarden op repo-niveau gelden voor elke environment en halen de hele opzet onderuit. | elke cd-\* met 1Password |
|  | `VM_SSH_HOST` en `VM_SSH_USER` per environment; `VM_SSH_PORT` alleen als de poort niet 22 is. | cd-swarm |
|  | `SUPABASE_PROJECT_REF` per environment. Staging en productie zijn aparte Supabase-projecten; een waarde op repo-niveau zou ze allebei naar één project laten wijzen. | cd-supabase |
| Secrets, op de environment | Alles waarmee gedeployd wordt: `OP_SERVICE_ACCOUNT_TOKEN`, `VERCEL_TOKEN`, `VM_SSH_PRIVATE_KEY` en `SUPABASE_ACCESS_TOKEN` (machine-account met Administrator op de Supabase-org) op `staging` en `production` ([besloten](../beslissingen.md#decided)). Zo staat het in gp-map, gp-groot en template al; tellr heeft `VERCEL_TOKEN` nog op de repo. Op `integration` alleen `OP_SERVICE_ACCOUNT_TOKEN`, en alleen als CI 1Password laadt; dat item mag dan niets bevatten wat een PR niet mag zien. Niet op org- of reponiveau: zo'n secret leest elke run op elke branch, ook de CI van een PR, en de YAML van die run komt van de PR. Een environment-secret zit achter de branchregels en de reviewers van de environment. | elke cd-\* |
| Dependabot-secrets, op org-niveau | Dezelfde waarden als de Actions-secrets die CI nodig heeft: `CUSTOM_GITHUB_TOKEN`, en `OP_SERVICE_ACCOUNT_TOKEN` als CI 1Password laadt. Een run die Dependabot start, krijgt alleen Dependabot-secrets, ook bij een push; zonder deze faalt de install van private pakketten en staat elke Dependabot-PR rood. | repo's met private pakketten of 1Password in CI |
| Secrets, op repo-niveau | Alleen wat CI op elke branch nodig heeft of wat niet geheim is: `CUSTOM_GITHUB_TOKEN` zodra `use-custom-token` gezet is (leestoegang op pakketten; zie de [detailbeslissing](detailbeslissingen.md#decisions-detail) om hem kwijt te raken). `VERCEL_ORG_ID` en `VERCEL_PROJECT_ID` voor cd-vercel; twee apps in één repo hebben twee project-id's en geven die per deploy-job expliciet door. `VM_SSH_KNOWN_HOSTS` voor cd-swarm. `TMS_URL` en `TMS_API_KEY` alleen als het 1Password-item ze niet bevat. | per target |
| Rechten van de aanroeper | `packages: write` voor cd-swarm, ook voor een stack van kant-en-klare images: GitHub toetst de rechten van elke job bij het starten, ook van de buildjob die dan wordt overgeslagen. `pages: write` en `id-token: write` voor cd-pages. `packages: write` voor cd-packages. `actions: read` voor cd-gate. Een aangeroepen workflow kan nooit meer rechten hebben dan zijn aanroeper geeft. | per target |
| Scripts en versies | Een `package.json` met een script per check, ook in Python-projecten, mét `packageManager` en een `pnpm-lock.yaml`: `--frozen-lockfile` eist beide. Een `turbo.json` zodra er meer dan één pakket is. `.nvmrc`, en bij Python `.python-version`. | altijd |
| Migraties | Alleen vooruit, en backward-compatible met de app die nog draait (expand/contract): migraties draaien vóór de app, en er is [geen rollback](../beslissingen.md#decided). Een kolom verwijderen gebeurt pas in de release ná de release die hem niet meer gebruikt. | cd-supabase, cd-swarm met `migrate-image` |
| Env-validatie bij de build | De app controleert zijn environment-variabelen tijdens de build en faalt bij een ontbrekende of lege waarde (bijv. een zod-schema of `@t3-oss/env-nextjs` in Next.js). Stackbestanden gebruiken `${VAR:?}` voor alles wat verplicht is. Zo is de build in CD zelf een controle, in plaats van een deploy die ongemerkt met `undefined` live gaat. | cd-vercel, cd-swarm |
| Verplichte workflows | Geen `paths:` op workflow-niveau: een workflow die niet start, laat zijn check op "Expected" staan. Wijzigingen detecteren gebeurt in de workflow (turbo `--affected`, het paths-filter van ci-images), zodat de check altijd een resultaat geeft. Zo kan ook de image-check verplicht worden. | altijd |
| CODEOWNERS | `.github/CODEOWNERS` met één regel voor de hele repo: `* @Pursuit-Amsterdam/senior-developers`. Met "review van code owners verplicht" betekent dat: een junior heeft de review van een senior nodig, niet van een andere junior ([besloten](../beslissingen.md#decided)), en een PR die zijn eigen CI aanpast ook. Org-owners en admins die reviewen, zitten in dat team. | altijd |
| Rechten | Team `senior-developers` admin, `developers` push, `project-managers` maintain. Directe admin-rechten voor een persoon alleen als die senior is; een directe admin buiten het team kan zijn eigen PR mergen zonder review. | altijd |
| Codegen | Gegenereerde code komt uit een script in de repo dat op de runner draait, niet uit de Dockerfile. Haalt het script iets van buiten de repo op, zoals een OpenAPI-spec, dan wordt dat bestand gecommit en als `codegen-baseline` opgegeven; het is de basis waarmee CD vergelijkt. | repo's met codegen |
| Base images | `FROM` vastgezet op een digest (`image:tag@sha256:…`), bijgewerkt door Dependabot. Anders bouwt CD op een ander base image dan ci-images testte. | repo's met een Dockerfile |
| Triggers | CI: `push` op `main`, `develop` en `acceptance` (als die er is), plus `pull_request`. Een mergecommit op een deploybranch moet zijn eigen CI-run hebben, anders is er niets dat CD start. Geen aparte trigger voor `dependabot/*`: die krijgt dezelfde secrets als de PR-run en geeft alleen een dubbele run. CD: `workflow_run` van `Continuous Integration` met `types: [completed]` en `branches: [develop]` (plus `acceptance` als die er is), nooit `push` ([besloten](../beslissingen.md#decided)); de gate-job heeft `if: github.event_name != 'workflow_run' \|\| github.event.workflow_run.conclusion == 'success'`, zodat rode CI een grijze CD-run geeft. Daarnaast `release: published`, `workflow_dispatch` zonder inputs (het doel komt uit de gekozen branch of tag), en `repository_dispatch: [tms-deploy]` zodra het vertalingen-CMS meespeelt. | afspraak; de naam, de branches, de `if:` en een CD-aanroeper met `push` controleert het auditscript |
| Dependabot | `.github/dependabot.yml` aanwezig. Gebruikt de repo private `@pursuit-amsterdam`-pakketten, dan staat er een registry in voor GitHub Packages, anders kan Dependabot die pakketten niet bijwerken: `registries: github-npm: type: npm-registry, url: https://npm.pkg.github.com, token: ${{ secrets.CUSTOM_GITHUB_TOKEN }}`, en `registries: [github-npm]` bij de npm-update. | altijd; registry bij private pakketten |

## Controleren: `scripts/audit-consumers.sh`

- **Alleen lezen, één regel per bevinding.** Loopt alle niet-gearchiveerde repo's van de organisatie af en controleert de repo's die deze workflows gebruiken, of krijgt reponamen als argument. Code search is daarvoor niet betrouwbaar genoeg: de resultaten zijn begrensd en missen bestanden. Per repo: welke workflowbestanden er zijn en welke ref ze gebruiken, verplichte checks en beschermingsinstellingen op `main` en `develop`, environments en hun schrijfwijze (`acceptance` zodra die branch bestaat), de branchregels en reviewers per environment, variabelen per environment, waar de deploy-secrets staan (op de environment, en niet ook op de repo), namen van reposecrets (ook `VM_SSH_KNOWN_HOSTS` voor cd-swarm), de rechten die de aanroeper geeft, de `name:` en de branches van de CI-trigger, en Dependabot: `dependabot.yml`, een registry voor GitHub Packages en de Dependabot-secret `CUSTOM_GITHUB_TOKEN` bij `use-custom-token`, en een overbodige trigger op `dependabot/*`. Exit 1 zodra er iets niet klopt. Een repo die het niet kan lezen, is een bevinding en stopt het script niet. Vereist `gh` met adminrechten op de repo's.
- **Wat het script van een repo verwacht, hangt af van wat die repo aanroept.** Een repo die alleen losse actions gebruikt, of alleen cd-pages, heeft geen `staging`/`production`, geen deploy-secrets en geen gate; het script meldt daar alleen check-pr, branchprotectie en Dependabot. Anders geeft elke library-repo een lijst bevindingen die niemand gaat oplossen, en verdwijnen de echte ertussen.
- **Branchprotectie:** leest de klassieke branchprotectie én rulesets, en meldt een verplichte check die niet aan GitHub Actions vastzit, geen review van code owners, meer dan één CI-workflowbestand of een CI-bestand met een andere `name:` dan `Continuous Integration`, een check-pr-aanroeper zonder `edited` of met een `branches:`-filter, `paths:` op workflow-niveau bij een verplichte CI-workflow, een `CODEOWNERS` zonder `* @Pursuit-Amsterdam/senior-developers`, en directe repo-admins die niet in `senior-developers` zitten.
- **Meldt ook resten van v1 en gaten in de CD-controles:** een workflow of action die nog op `@main` staat, een CD-aanroeper die nog lint of test herhaalt, die op `push` start in plaats van `workflow_run`, of waarvan de gate-job de `if:` op `workflow_run.conclusion` mist, en een Dockerfile met een `FROM` zonder digest. Zo volgt hetzelfde script de voortgang van de migratie.
- **Het bijbehorende `scripts/setup-consumer.sh <repo>`** past de standaard toe op een nieuwe of afwijkende repo: beveiligingsregels, environments, en de variabelen met lege waarden om in te vullen. Hier niet uitgewerkt; de controles van het auditscript beschrijven wat het moet doen.
- **Hulpworkflow `audit-consumers.yml`** draait het script wekelijks in deze repo en werkt één issue bij met het rapport. Een nieuw gat zie je dan als wijziging in dat issue, niet pas tijdens een incident. Het leest met een GitHub App met alleen-lezen rechten (administration, environments, secrets-metadata) op de org, niet met een admin-PAT: een PAT van een beheerder in een reposecret is precies het soort secret dat elke branch van deze repo zou kunnen lezen. De app-credentials staan op een environment `audit` met als enige toegestane branch `v2`.
- **Staat in deze repo**, naast `check-pr.sh`: na check-pr het tweede script dat iets controleert, en het eerste dat naar andere repo's kijkt.
