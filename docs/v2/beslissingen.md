# Beslissingen

De keuzes die de principes of de beveiliging raken, met per keuze wat besloten is en waarom. Kleinere uitvoeringskeuzes staan in de naslag: [detailbeslissingen](naslag/detailbeslissingen.md#decisions-detail).

<a id="decided"></a>

## Besloten

- **Geen rollbacks.** CD rolt alleen vooruit. Een handmatige start deployt de head van de branch van die environment, voor productie de nieuwste release; een oudere tag of commit kiezen kan niet. Herstellen is een nieuwe commit of release die CI opnieuw goedkeurt. Gevolgen: geen `dispatch-ref` in de gate; migraties zijn alleen vooruit en moeten daarom backward-compatible zijn (expand/contract: eerst toevoegen, pas later verwijderen), omdat ze vóór de app draaien en een mislukte deploy de oude app tegen het nieuwe schema laat draaien; een gefaalde health-check maakt de run rood en meldt het CMS, meer niet. Swarm-repo's kunnen `failure_action: rollback` in hun stackbestand zetten, dat is Swarm zelf, geen CD.
- **CD start alleen op `workflow_run`, nooit op `push`.** Bij een `push`-trigger starten CI en CD tegelijk, en zou de gate moeten wachten tot CI klaar is: een runner die tot een half uur niets doet, bij elke push. Met `workflow_run` start CD pas als de CI-workflow klaar is, en leest de gate alleen nog af: geslaagd, op welke commit, en ben ik het laatste signaal. gp-map en gp-container-tracking doen dit al. Na een `workflow_run` wacht de gate daarom nooit. Bij een release of een handmatige start wél (20 oktober 2026): een release publiceer je direct na de merge naar `main`, en dan loopt CI op die commit nog. De gate kijkt elke 30 seconden, hooguit `ci-wait-minutes` (standaard 20), en faalt meteen als CI faalt. Eén wachtende runner per release; zonder dat faalde de eerste release van pursuit-website-2025 met 17 seconden verschil. Een repo die na de migratie toch nog op `push` staat, krijgt een gate die meteen faalt met "geen CI-run voor deze commit"; dat is zichtbaar en lost zichzelf op. Het migratiescript herschrijft de trigger; het auditscript meldt een CD-aanroeper met `push`.
- **Een release deployt productie; een merge naar `main` niet.** `main` staat niet in de standaardkoppeling van de gate (`develop=staging acceptance=acceptance`), dus een merge naar `main` levert alleen een groene CI op. `release: published` start de deploy, op de commit van de tag, mits de CI op `main` daarop geslaagd is. Een repo die wél bij elke merge live wil, zet zelf `main=production` in `branch-targets` en `main` in de branchregels van zijn `production`-environment. **De nieuwste release opnieuw deployen mag**, bijvoorbeeld na een wijziging in 1Password: dat is dezelfde commit nog een keer, geen rollback. Twee manieren: *Re-run all jobs* op de laatste CD-run, of `workflow_dispatch` met `environment: production`, gestart vanaf de tag van die release ("Use workflow from" → Tags). Vanaf de tag, omdat de branchregels van `production` alleen tags toelaten; een dispatch vanaf `main` weigert GitHub. De gate controleert dat de tag de nieuwste release is en weigert een oudere.
- **Het CMS (`tms-deploy`) deployt alleen naar staging, nooit naar productie.** Een `repository_dispatch` draait op de default branch, en `production` laat alleen tags toe; GitHub zou zo'n deploy weigeren, en de gate weigert het verzoek daarom meteen met die uitleg. Vertalingen voor productie gaan mee met de volgende release. Wie een CMS-deploy naar productie wil, publiceert een release.
- **Handmatig starten: het doel komt uit de branch of tag waarvan je start.** Geen `environment`-keuzelijst in de aanroeper. "Use workflow from" → `develop` deployt staging, → `acceptance` deployt acceptance, → de tag van de nieuwste release deployt productie. Overgenomen van gp-map: het gedeployde environment kan zo nooit afwijken van wat je koos, en het sluit aan bij de branchregels van de environments.
- **Eén CI-workflowbestand per repo, met de naam `Continuous Integration`.** Meerdere CI-jobs (bijvoorbeeld `run-ci` en `run-ci-images` in een Swarm-project) staan als jobs in dat ene bestand. Eén bestand geeft één `workflow_run`-event, dus één gate-run per commit; de ontdubbeling in de gate blijft als vangnet voor wie afwijkt. `required-workflows` staat daardoor standaard op die ene naam.
- **Elke repo heeft een `package.json`, ook zonder node.** De scripts erin zijn de namen waarmee CI de checks aanroept (principe 7); een Python-repo zet er `"lint": "uv run ruff check ."` in. Het alternatief, een apart Python-pad in ci.yml met vaste uv-commando's, geeft weer twee paden. Het kost drie kleine bestanden: `package.json` met een `packageManager`-veld, een `pnpm-lock.yaml` (mag leeg zijn) voor `--frozen-lockfile`, en `.python-version`.
- **Turbo is verplicht zodra er meer dan één workspace is.** Eén job voor frontend én backend, caching, en bij een PR alleen de pakketten die veranderd zijn. Tien repo's gebruiken turbo al: gp-map-webapp (op develop), tellr-webapp, web-essentials-js, integrators-automations, automations-blueprint, big-chef-webapp, text-extract, nextjs-feature-flags, den-haag-casusregie-automations en miracle-admin-hub (op develop). Eén pakket: gewone scripts.
- **Staging is één vaste omgeving waar `develop` heen gaat; niets per pull request.** Op Vercel is staging het custom environment `staging` van het project: de `develop`-branch, met een eigen vaste URL. Zo staan de Vercel-projecten al ingericht, en v2 verandert daar niets aan (20 oktober 2026; eerder stond hier "de preview-deploy van `develop`", dat was verkeerd geformuleerd). Geen preview per PR. cd-vercel deployt `staging` met `vercel pull --environment=staging` en `--target=staging`, zoals v1, met de variabelen van de GitHub-environment `staging` (1Password) erbij. Elke andere environment dan `staging` en `production` weigert hij (acceptance op Vercel is niet besloten, en een typfout mag nergens heen deployen). Op Supabase is staging één vast project (`vars.SUPABASE_PROJECT_REF` op `staging`) waar `develop` heen migreert; geen Supabase-branching per PR. Use case 25 vervalt.
- **`pre-deploy` draait als de deploy-gebruiker, zonder sudo, en controleert alleen.** Het script toetst of de server klaar is voor de stack: bestaat de map voor de certificaten, is het externe netwerk er, staan de node-labels goed. Ontbreekt er iets, dan faalt het script en stopt de deploy voordat er iets aan de Swarm verandert. Het script maakt niets aan en wijzigt niets op de host; inrichten (mappen en hun eigenaar, `sysctl`, sudoers, Docker zelf) hoort bij de VM en komt met [infra as code](use-cases.md#iac). Tot dan is dat een handmatige runbookstap, en `pre-deploy` is de controle dat die stap gedaan is. Sudo voor de deploy-gebruiker voegt niets toe: wie in de groep `docker` zit, kan via een bind mount toch al alles op de host; de beveiliging ligt bij de branchregels van de environment en wie bij `VM_SSH_PRIVATE_KEY` kan.
- **Alle deploy-credentials zijn environment-secrets, ook `SUPABASE_ACCESS_TOKEN`.** `OP_SERVICE_ACCOUNT_TOKEN`, `VERCEL_TOKEN` en `VM_SSH_PRIVATE_KEY` staan in de praktijk al op `staging` en `production`; het Supabase-token komt daar ook, gezet door de org-admin die het beheert, per repo en per environment. Een org- of reposecret leest elke run op elke branch van de repo, ook de CI van een PR; alleen een environment-secret zit achter de branchregels van het environment. Het is wat knip- en plakwerk voor de paar repo's die naar Supabase deployen, en dat is het waard.
- **cd-supabase en de app-deploy: na elkaar, Supabase eerst.** De deploy-job van de app heeft `needs:` op die van Supabase, zodat de app nooit live gaat vóór de functions en migraties die hij nodig heeft. Een storing bij de Supabase-API houdt dan ook een release tegen die er niets mee te maken heeft; dat is de prijs.
- **Senior developers mogen hun eigen PR mergen; iedereen anders heeft een review nodig.** Zo is het nu al in de consumer-repo's, en zo blijft het, ook op `v2`. Het hangt aan de rol: `senior-developers` is admin op elke repo, `developers` heeft push, en admins mogen de verplichte review overslaan, alleen bij een PR. De verplichte checks (`run-ci / pipeline`, `run-check-pr / pipeline`, op `v2` `pipeline`) gelden voor iedereen, ook voor seniors: ze staan in een aparte ruleset zonder bypass. Nu, met klassieke protectie en `enforce_admins: false`, kan een admin ook langs een rode check mergen; dat verdwijnt bij de overstap. Op `v2` laat een senior PR's die de gate of secrets raken bij voorkeur toch door een tweede senior reviewen. **Een junior laat reviewen door een senior, repo-admin of org-owner, nooit door een andere junior.** GitHub dwingt "van wie" alleen af via CODEOWNERS: elke repo krijgt `* @Pursuit-Amsterdam/senior-developers` en "review van code owners verplicht". Wie mag reviewen, staat daarmee in één team: org-owners en admins die reviewen, horen in `senior-developers`. Directe admin-rechten op een repo krijgen alleen seniors, anders kan een junior via die rechten toch zijn eigen PR mergen.
- **Alleen seniors deployen naar productie, via de release-tag.** Verplichte reviewers op een environment bestaan voor privé-repo's alleen in Enterprise; op het Team-plan weigert GitHub ze. Daarom: een tag-ruleset op `v*` laat alleen admins (`senior-developers`) een `v*`-tag maken, wijzigen of verwijderen, en een release heeft zo'n tag nodig. Het environment `production` laat alleen `v*`-tags toe, zodat geen branch bij de productie-secrets kan. Een handmatige start vanaf de tag van de nieuwste release mag ook een junior; dat is dezelfde code die al live staat, en de gate weigert elke oudere tag.
- **`staging` en `acceptance` laten ook `main` toe.** GitHub toetst de branchregel van een environment tegen de ref van de run, en bij `workflow_run` (de gewone deploy na een merge) en `repository_dispatch` (het CMS) is dat altijd de default branch. Met alleen `develop` kwam geen enkele automatische deploy door (gevonden bij het testen van de gate). Die runs draaien de beschermde `cd.yml` van `main`; welke commit live gaat, bepaalt de gate, en een handmatige start vanaf `main` weigert hij.
- **Branchprotectie per repo, niet centraal.** Zo kan een repo afwijken als dat nodig is. Het is op het Team-plan ook de enige optie: rulesets op org-niveau voor private repo's, "Require workflows to pass" en de merge queue zijn Enterprise-functies. De standaard staat in de [standaardinrichting](naslag/standaardinrichting.md#consumer-config); `setup-consumer.sh` zet hem, en de wekelijkse audit meldt elke afwijking, zodat een bewuste afwijking bekend is en een onbewuste opvalt. De checknamen blijven `run-ci / pipeline` en `run-check-pr / pipeline`.
